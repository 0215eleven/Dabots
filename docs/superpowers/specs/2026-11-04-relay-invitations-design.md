# Official relay phone invitations

Authorized request: replace relay-admin approvals with server-generated invitations. One invite enrolls one phone; an enrolled phone may scan multiple computers. No production, release, key provisioning or repository-permission changes in this task.

## Approach and decisions

Use the existing Node/Ed25519/X25519 stack. The server stores invited phone public keys and computer associations. The phone keeps a fresh Ed25519 private key in device-only Keychain storage, scoped by relay origin, without cloud sync. Web previews keep keys in memory. An embedded package-wide key is extractable and will be removed from admission and packaging. A bearer-only invitation on every connection would allow copying/replay; client-only checks would permit bypass. Those alternatives are rejected by the authorized security requirements.

The invitation is random (192 bits), displayed only by an explicit operator CLI command, hashed on disk, one-use and expiring. Redemption must prove possession of the enrolling public key through a signed request. Serialize mutations; durably write an immutable candidate before publishing state. A failed disk write grants nothing. Duplicate simultaneous redemption produces exactly one winner. Reinstall/lost phone requires a new invitation; no automatic transfer/re-enrollment of revoked identities.

Operator commands create/list/revoke via an exclusive access-store lock. The relay holds the lock for its lifetime; offline CLI refuses while it runs. Stop the service for CLI changes, then restart. This deliberately small operational interface avoids exposing a remote admin API or local unauthenticated HTTP admin port. Runtime in-process revocation notifies active connections synchronously after durable commit. Stop-before-offline-revoke also guarantees no forwarding after revocation. Never delete a stale lock without first verifying the old process has exited.

## Protocol

Invite mode is explicitly configured by RELAY_ACCESS_FILE and cannot be combined with legacy registration/accounts/approval/build-key admission. It fails closed with invalid/corrupt/missing stores. A migration command initializes an explicit empty store. Old approval stores are never imported as invitations. Legacy RELAY_OPEN_REGISTRATION and RELAY_APPROVALS_FILE/RELAY_BUILD_KEY_FILE cause startup refusal rather than exposing registration. Secret/account self-hosted relay modes remain separate; direct pairing is unchanged.

Computers prove Ed25519 identity with a fresh server nonce and a v3 signed transcript binding relay origin, nonce, computer ID, Ed public key, X public key and serverId. They first wait for an enrolled phone. Each live registration has a random 256-bit link nonce, expiring after five minutes; the server remembers its complete exact identity tuple. The server sends fresh link controls every four minutes so a long-running computer remains scannable; changed link context invalidates stale pairing leases. The plugin includes this nonce and protocol marker in QR pairing data, never an invitation. A signed phone association request must match that current registration and nonce. A computer is owned by one phone; the same active phone may scan it again and own multiple computers. Ownership cannot be stolen by a different enrolled phone. After revocation, a replacement invited phone may take the association only with a fresh QR from the live computer; the revoked phone stays unauthorized. Changes to a bound computer's key/server identity fail closed. Reconnection keeps durable ownership but rotates the link nonce; stale QR association is refused. QR lease handling preserves the safe same-identity pending-to-ready transition and invalidates changed contexts.

Every phone WebSocket receives a fresh authentication challenge before the relay opens any stream to a computer. Its signed transcript binds the challenge to relay origin and exact computer tuple. Require an active enrolled key and matching association. No authorization tokens/signatures in URLs. Check authorization in both forwarding directions, not only handshake. Revocation removes authority immediately after durable commit, closes computer/phone sockets and prevents reconnect/old proofs. Unknown/revoked keys, unsigned/old clients, forged association, replay and expiry are refused. Existing rate, byte, stream and connection limits also apply before authentication; bounded request bodies/caches/records prevent resource exhaustion. Native HTTPS Origin policy and end-to-end encrypted RPC stay intact.

Signed HTTP requests bind method, canonical path, relay origin, timestamp, random request nonce and SHA-256 body. Reject query strings, browser origins, malformed/noncanonical encodings, stale requests and repeated signatures/nonces. Short-lived replay cache is bounded; security-sensitive replays across restart also fail because invitations are spent and computer nonces rotate. Responses/errors/logging never echo invitations, request bodies, keys or signatures.

## App and compatibility

Replace relay-admin routes/keys/approve helper with an Official connection invitation page accessible before pairing and from settings, with back-to-pairing, draft preservation, busy state, dark/light and Chinese/English. Redeem only against the configured official origin. The screen clears the invite after sending and never logs/caches it. All relay clients provide a signing callback to the SDK; legacy self-hosted relay protocol remains usable, but a configured official relay must demand new authentication and must not downgrade to an old open endpoint. Existing hosts/slots, encrypted data and Bridge's computer-side phone-pairing approval remain; Bot/action approvals remain untouched.

Existing official host credentials are retained, but secure migration cannot infer new phone ownership from old public computer IDs: the user enrolls this phone and scans each computer once. No migration grants authority automatically. Old service versions cannot safely serve the invitation policy: rollback requires stopping the service and restoring a closed configuration/firewall, never re-enabling public registration. Keep backup stores and source versions; do not downgrade a running invite store into legacy approval/account state.

## Verification

Start with failing behavioral tests for enrollment, duplicate/concurrent redemption, crash/disk failure, store locking, expiry/replay, revoked-key re-enrollment, wrong origins and malformed state. Use real HTTP/WebSocket tests for uninvited access, forged/mismatched/expired QR association, two phones/two computers, authenticating before opening streams, reconnect/restart and revocation of both directions. Run the real SDK/Bridge encrypted probe, including native Origin; ensure old direct/self-hosted pairing and all unrelated action approvals survive. App tests cover fresh-phone enrollment/back/draft/busy/error/retry, storage concurrency, exact official-origin enforcement and signer use on restored hosts. Run setup/prepare/check, integration/suite, packed-delivery and artifact audit. Native build/real-device validation are separate and will be reported unavailable if not performed.
