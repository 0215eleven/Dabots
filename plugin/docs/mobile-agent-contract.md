# Mobile DSH Agent: contract and owner-accepted boundary

Status: **implemented with the owner's per-device grant (2026-10-24).** The design
below was written as a blocked contract on `main` `dbc567c`. On 2026-10-24 the
repository owner chose to enable Agent creation and plain-text chat on phones
the owner explicitly allows, **accepting** the secret-redaction limitation
described in the next section. "Implemented" below means: the engine patch,
Bridge, companion and App changes listed in [What was implemented](#what-was-implemented),
with unit, patched-channel and real-fixture integration tests. It does not
remove the limitation, and no physical-device acceptance has been performed.

## What was implemented

| Requirement in this design | Implementation |
| --- | --- |
| Distinct negotiated contract; no fallback from a bare flag | `bridge.describe` advertises `agents: 1`. The Bridge enables Agents only when `version: 1`, `stableRequestId`, `redactedText` and `agents === 1` are all present (`agentsSupported()` in `bridge/src/adapter.mjs`). `agents: true`, `2` or partial contracts stay closed. |
| Per-device owner grant, default denied, phone cannot self-grant | `device.agents` is an **owner operator** request only (DSH owner carrier). Devices start without it; re-pairing creates a new device record without it. The companion's paired-device list shows an "Allow DSH Agent" control that requires confirming a warning about global tools and unredacted provider/connector secrets; turning it off is immediate. |
| Grant revalidated on every request and stream frame | The server passes the current grant into `state`, `conversations`, `target`, `history`, `submit`, `cancel`, `read-markers`, `actions` and the WebSocket follow loop, which re-reads it per frame. Removing it closes the device's Agent streams. |
| Create or enter the Agent without client workspace/permission input | `agent-open` (no fields) → `bridge.agent-open`: creates the team's one Agent when absent, else returns its latest live Session (a new one only when it has none). `agent-new` (`agentId` only) starts a Session in the team workspace. Unknown fields are refused; the result must be a listed Agent Session. |
| Exact Agent-to-Session validation | The patch admits `agent:<agentId>` with an `expectedSessionId` only when that Session is in the Agent's live list and is not owned by a Bot, Room or group member. The phone conversation id is `agent:<agentId>:<sessionId>`; forged, cross-agent and Bot Session ids are refused. |
| Plain text only; approvals stay on the computer | Submit accepts one text block without `dsh-session:` references or attachments. The phone shows "approve it on the computer" while an Agent is running; it never resolves approvals. |
| Same projection for history and stream | Only user/assistant message text is released (no tool calls/results, reasoning or attachments), then passed through `bridge.redact`. |

Not implemented on the phone: Agent rename, archive, removal, adoption and
workspace switching remain computer-only.

### Accepted limitation

`bridge.redact` removes only values in DS Bot's own secret store. If the Agent
echoes a model-provider or connector credential in its reply, that text reaches
the allowed phone over the paired, encrypted Bridge connection. The owner
accepted this for phones they allow; the companion states it before the grant.

## Blocking safety boundary

A DSH Agent is the team's one container for ordinary root Sessions. It is not a Bot.
Its Sessions use the global DSH tool surface, excluding DS Bot's team tools; see
the vendored DS Bot 0.2.0 source snapshot's [`agents.js`](https://github.com/0215eleven/ds-bot-mobile-app/blob/dbc567cfb2b1474418c38347ae3c6815aa2ff78e/ds-bot/ds-bot/src/host/agents.js#L1), especially the tool restriction
and creation paths at lines 22-25 and 85-97. A mobile Agent grant would therefore
expose a different authority surface from existing mobile Bot access.

The shipped [`ds-bot-0.1.7-groups.patch`](https://github.com/0215eleven/ds-bot-mobile-app/blob/dbc567cfb2b1474418c38347ae3c6815aa2ff78e/group-bridge/patches/ds-bot-0.1.7-groups.patch#L17)
advertises `redactedText: true`, but its `bridge.redact` implementation calls
`rt.redactSecrets`. The inspected host, in the vendored DS Bot 0.2.0 snapshot,
[`secrets.js`](https://github.com/0215eleven/ds-bot-mobile-app/blob/dbc567cfb2b1474418c38347ae3c6815aa2ff78e/ds-bot/ds-bot/src/host/secrets.js#L38) builds that redactor from its
own secret-store entries (line 101), and exports it as `redactSecrets` (line 552).
The integrity-pinned DS Bot 0.1.7 fixture that the guard test imports has the same
functions at `bridge/fixture/vanilla/package/src/host/secrets.js` lines 37 and 544
(generated by `test:prepare`, not tracked); the behaviour cited here is identical in both.
That contract does not establish coverage of global provider or connector secrets.
A synthetic counterexample in
[`agent-boundary.test.mjs`](../bridge/test/agent-boundary.test.mjs) exercises the
actual integrity-pinned DS Bot 0.1.7 redactor with the Bridge formatting filter,
supplying a DS Bot stored value and distinct global
provider/connector sentinel values: the known stored value is removed while the
other values remain. By construction the test shows only that the redactor removes
the values it is given; that the host's store holds DS Bot secrets and not the
global provider/connector credentials rests on the source reading above, not on
the test. This proves a boundary limitation, not leakage from a real
user profile. No real credentials are needed or permitted for this test.

No documented public DSH API providing the necessary safe Agent projection has been
identified in the inspected sources; [the host evidence report](mobile-agent-host-evidence.md)
records the pinned API packages and their limits. Dropping tool cards is insufficient: user or
assistant text, names, queue content, errors and partial stream frames can also
contain sensitive values. A regex, the existing known-store redactor, or the
`redactedText` boolean alone must not be presented as global secret protection.

Consequently Agent capability stays off. The existing patch also validates only
Bots and Rooms in both `bridge.submit` and `bridge.redact`; an Agent target cannot
be admitted by merely changing mobile capability flags. The next implementation
requires a documented, versioned host projection with a reviewable threat model
and tests covering the Agent's actual surface. If that cannot be provided through
public plugin APIs, report the missing upstream API and stop. Do not patch DSH
internals or read all global credentials into the Bridge to manufacture a redactor.

## Required minimal contract (proposed, not implemented)

### Negotiation and owner consent

- `bridge.describe` must advertise a distinct, versioned Agent contract covering
  lifecycle, Agent-to-Session validation, stable admission IDs, safe projection,
  host approval status and queue behavior. Existing Bot/Room `version: 1`,
  `stableRequestId` and `redactedText` fields do not imply Agent support.
- Unknown, partial or older contracts disable Agent actions, listing, target,
  history, stream and submit. No permissive fallback from a bare `agents: true`.
- Support and authorization are separate. Existing paired devices receive no
  Agent grant automatically, including devices paired before the upgrade.
  The computer owner must explicitly select the Agent feature for a device via
  the authenticated owner carrier. The UI must explain ordinary DSH/global tool
  authority and existing host approval behavior. A phone cannot grant itself
  access. Development exercises this only with synthetic owner/device identities;
  real enablement requires the user's separate confirmation.
- Public `/info` currently returns global capabilities
  ([`server.js:192`](https://github.com/0215eleven/ds-bot-mobile-app/blob/dbc567cfb2b1474418c38347ae3c6815aa2ff78e/bridge/src/server.js#L192)). It may describe support but
  cannot authorize a particular device. An authenticated response must provide
  that device's effective Agent capabilities. Missing stored grant means denied.
  Each request and each stream emission must revalidate the effective grant;
  revocation cancels pending work that has not been admitted and closes live streams.

### Create or enter the team's Agent

- A narrowly validated operation accepts a stable `requestId` and no client
  workspace, directory, permission, credential, model or tool fields. Scope the
  durable operation to the authenticated device and team. Unknown fields fail.
- Serialize concurrent creation within the team. Create its only Agent and one
  default-team-workspace root Session when absent. If an Agent already exists,
  return a current valid owned Session deterministically; create a default-workspace
  Session only when none is eligible. Never create a second Agent or silently adopt
  an arbitrary Session. An existing Session outside the allowed initial scope must
  not be exposed just because it appears in the Agent record.
- Return explicit `agentId`, `sessionId` and canonical `conversationId`, with
  bounded, safely projected display fields. Do not make the phone infer selection
  from `sessions[0]`. A repeated operation with the same ID returns the recorded
  result; a conflicting payload fails. A lost response or restart must not create
  another Session. Revalidate the recorded target before exposing it; an archived
  result is stale, not a reason to reinterpret the same request as new creation.
- If a separate new-conversation action is needed, its only inputs are `agentId`
  and a stable `requestId`, with the same checks. The first release does not add
  Agent rename, archive, remove, adopt, workspace switching or management features.
  Existing computer-side archive/remove operations remain relevant race conditions.

### Ownership, text delivery and approvals

- Derive team scope from the authenticated host context. Resolve Agent and Session
  using current authoritative records. Validate that the Agent exists in that team,
  the Session belongs to it, is a live eligible root Session, and is not owned by a
  Bot, Room or another Agent. Parsing an ID or finding a Session alone is insufficient.
- Apply the check to listing, target, action replay, submit/receipt recovery,
  redact/projection, history pages/cursors and every stream update. Recheck after
  asynchronous boundaries and before admission or emission. Reject stale,
  archived, removed, cross-team and forged targets without exposing their data.
- Keep the existing once-created outgoing `requestId`, bound to device,
  conversation and exact Session. The host admission uses that same stable ID
  across retries and Bridge restarts. Return `accepted` only for actual host
  admission; it does not mean the turn completed. Unknown outcomes remain unknown.
  Re-pairing must not retry an old device's pending send.
- Send plain text only. Reject attachments, raw tool payloads, arbitrary Session
  references, directories, permissions and credentials. Keep host prompts on the
  normal approval path. The phone does not approve or automatically allow tools.
  A safe approval-wait status must tell the user to continue on the computer.
- Specify and test queue admission, ordering, duplicate replay and restart behavior.
  Do not conflate `accepted`, queued, running, blocked and completed. If stop/removal
  is not in the initial Agent contract, keep those controls disabled; if supported,
  stopping execution must not silently discard queued messages. Existing Bot/Room
  queue behavior must remain unchanged.
- History and stream must use the same explicit safe projection. Exclude raw tool
  arguments/results, reasoning, attachments and unreviewed metadata. Secret
  handling must cover every allowed string and partial output; withholding all
  assistant output would not satisfy the requested chat feature.

## Versions, provenance and installation boundary

This change moves the combination to App source `0.1.8-codex.2`, SDK
`0.1.1-codex.2`, Bridge `0.0.9-codex.4` and companion `0.2.1-codex.3`, and adds
the compatible engine **`ds-bot@0.1.7-agent.1`**: public, integrity-pinned
`ds-bot@0.1.7` with the checked-in patch applied to `src/host/channel.js` only,
the original LICENSE retained and a `PATCHED.md` notice added. Build it with
`npm --prefix bridge run test:prepare && npm run pack:ds-bot`.

Installing that engine replaces the DS Bot on the computer. It is built from the
public 0.1.7 package plus this repository's patch, so any other customisation in
an existing compatible engine (for example a separately built
`ds-bot-0.1.7-codex.1.tgz`) is not carried over. Keep the previous archive for
rollback. The separate vendored DS Bot source snapshot declares 0.2.0 and is not
interchangeable with the pinned fixture.

This work does not build a phone package, install into the daily DSH profile,
start a tunnel, modify real pairings/credentials/permissions, or enable Agent access.
The draft PR must remain described as blocked design and guards, not end-to-end
feature completion, and must not be merged automatically.
